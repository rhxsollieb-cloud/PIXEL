这套软件的设计哲学，我会把它概括为一句话：

**把“功能”从界面上拿掉，把“能力”放进对象、动作、上下文和语言里。**

它不是传统意义上的视频编辑器，也不是“给 Premiere 加一层 AI”。它更像一种面向生成模型重新设计的创作环境：界面尽可能安静，功能尽可能隐形，操作路径尽可能唯一，而真正的复杂度被放在弹窗、对象关系、上下文菜单、命令行和 Agent 能力中。

## 1. 界面不是功能目录，而是作品本身

传统软件的一个根本假设是：软件有什么能力，就要让用户看见什么按钮。

所以功能越多，工具栏越长，菜单越深，面板越多。

你的设计恰恰相反。

用户打开软件时，不应该先看到“这个软件能做什么”，而应该看到：

**画面 + 时间。**

也就是 Viewer 和 Timeline。

这两个东西不是工具，而是作品本身的两个基本维度：空间结果和时间结构。

因此默认界面甚至可以接近：

```text
┌──────────────────────────────┐
│                              │
│            VIEWER            │
│                              │
├──────────────────────────────┤
│                              │
│           TIMELINE           │
│                              │
└──────────────────────────────┘
```

其他所有东西都暂时不存在。

软件的复杂度不是铺在桌面上的，而是在用户做出动作之后才出现。

这就是整个产品最核心的“安静感”。

---

## 2. 无按钮不是视觉风格，而是架构原则

这里的“无按钮设计”不能简单理解成把按钮隐藏起来。

真正的含义是：

> **如果一个行为可以通过对象关系、上下文或者直接操作自然表达，就不再创建额外按钮。**

例如：

打开项目，不需要“Open Project”按钮。

用户把项目拖进窗口，就是打开。

导出视频，不需要长期存在一个 Export 按钮。

用户从 Viewer 把结果拖出去，就是导出。

进入 Clip 设置，不需要 Inspector 按钮。

用户双击 Clip，就是进入。

创建时间线，也不需要 Add Track 按钮。

Timeline 空白区域右键，就是创建。

因此 UI 控件不是默认答案。

只有当某个功能无法通过已有交互语法自然表达时，才考虑增加新的显式控件。

这会让产品长期保持极简，而不是“第一版极简，第三版开始长满按钮”。

---

## 3. 固定单路径，比“方便”更重要

这一点可能是你整个系统最重要的工程哲学。

传统软件会认为：

> 一个功能有越多入口越方便。

比如：

添加模型可以按钮添加、菜单添加、拖进去、快捷键添加、右键添加。

从传统 UX 看，这似乎叫“灵活”。

但对你的系统来说，这是负资产。

因为每增加一个入口，就意味着：

前端要维护更多状态路径，Agent 要理解更多等价操作，文档要解释更多方式，测试要覆盖更多组合，用户也要判断“我应该用哪一种”。

所以你的原则应该是：

> **一个能力只有一条标准路径。**

例如创建模型时间线已经决定：

```text
Timeline 空白处右键
→ New Timeline
→ Model
```

那么就不要再允许：

```text
模型拖进 Timeline
```

即使这个行为看起来“也挺直觉”。

因为拖拽应该留给真正需要空间关系表达的行为。

这会形成一个非常强的系统特征：

**不是功能少，而是路径少。**

功能可以非常深，但每个功能只有一条明确入口。

这会大幅降低软件复杂度。

---

## 4. 整套软件应该只有三种核心动作

最终可以把所有 GUI 行为压缩成三个基本语法：

### 双击：进入

双击永远表达：

> **我要进入这个对象。**

双击 Clip，打开 Clip。

双击 Timeline，进入 Timeline 设置。

双击资产，进入资产详情。

双击生成任务，进入生成历史。

这意味着用户不需要猜：

“这个东西双击会播放？编辑？重命名？打开？”

最好永远只有一个答案：

**进入。**

---

### 右键：这个对象还能做什么

右键承担离散操作和创建操作。

例如：

```text
Timeline 空白
→ New Timeline
→ Paste
→ Timeline Settings
```

```text
Clip
→ Regenerate
→ Split
→ Duplicate
→ Delete
```

右键的语义不是“高级功能”，而是：

> **当前对象在当前上下文中的 Action 集合。**

因此右键菜单应该高度上下文化，而且数量有限。

不要一次返回几十个动作。

---

### 拖拽：改变空间关系或对象关系

拖拽应该是最严格的一类。

因为拖拽最容易失控。

所以你可以规定：

> **只有当动作本身具有明确的 Source → Target 关系时，才允许使用拖拽。**

例如：

```text
项目文件 → 软件
= 打开项目
```

```text
Viewer → 文件系统
= 导出视频
```

```text
Asset → Timeline
= 创建 Clip
```

```text
Clip → Asset Library
= 保存为资产
```

```text
Reference → Clip
= 建立引用关系
```

而重新生成、切换模型、复制、删除，这些没有真正的空间关系，就不应该使用拖拽。

所以拖拽不是“快捷操作”。

拖拽是**关系语言**。

---

## 5. Modal 不是弹窗，而是“进入另一个认知空间”

你的弹窗设计与普通软件也不同。

普通软件里的 Modal 是：

“出现一个设置框。”

你的 Modal 更应该理解为：

> **用户暂时离开全局世界，进入某个对象自己的世界。**

因此它必须具有很强的隔离感。

主界面可能非常简单。

用户双击一个 Clip：

```text
┌─────────────────────────────┐
│ VIDEO CLIP                  │
│ Generated video · 6.2 sec   │
│                             │
│        [ Preview ]          │
│                             │
│ Prompt                      │
│ A woman walking...          │
│                             │
│ References                  │
│ 3                           │
│                             │
│ Generation                  │
│ Veo                         │
└─────────────────────────────┘
```

这时候用户不应该同时被 Timeline、资源库、模型面板、参数面板吸引。

当前唯一重要的东西就是：

**这个 Clip。**

如果继续点 References，Modal 内容发生切换。

而不是：

Modal 上再弹 Modal，再弹一个侧栏。

所以更准确地说，你不是在设计“弹窗系统”。

你是在设计一个：

**Context Navigation System。**

主界面是 Level 0。

对象详情是 Level 1。

对象内部信息是 Level 2。

每深入一层，认知范围更小。

然后 Esc / Back 返回上一层。

---

## 6. Progressive Disclosure 要做到的不只是隐藏参数

普通的 Progressive Disclosure 是：

简单设置默认显示，高级设置点开。

你的版本应该更激进。

它应该控制：

**功能什么时候存在。**

比如用户没有 Timeline 时：

模型参数甚至没有必要存在。

用户没有选择 Clip 时：

Regenerate 也不存在。

没有 Reference 时：

Reference Management 也没有必要出现。

只有当上下文成立以后，功能才“出生”。

也就是说：

> **UI 不是一个完整功能树的折叠版本，而是根据当前状态动态生成的能力表面。**

这很重要。

因为它最终也会直接服务 Agent。

---

## 7. Agent 不应该“操作 UI”

这是另一个非常核心的理念。

Agent 不应该做：

```text
点击 x=120 y=400
等待窗口
点击第二个按钮
拖到这里
```

那只是 UI Automation。

你真正要做的是：

```text
GUI
CLI
Agent
```

三者共享同一个 Action Layer。

例如用户右键选择：

```text
Regenerate
```

实际上调用：

```text
clip.regenerate()
```

CLI 可以调用：

```text
regen current
```

Agent 调用：

```text
clip.regenerate(id)
```

三个入口最终执行同一个 Action。

所以整个系统应该是：

```text
GUI ─────┐
         │
CLI ─────┼──→ ACTIONS ───→ PROJECT STATE
         │
Agent ───┘
```

而不是：

```text
Agent → 模拟 GUI
```

这样 GUI 才不会成为系统的中心。

真正的中心是：

**Project State + Action System。**

---

## 8. GUI 与 CLI 应该是同一种语言的两种表达

这是这套产品很有价值的地方。

GUI 表达空间关系。

CLI 表达语言关系。

例如 GUI：

```text
把 reference.jpg
拖到 clip_03
```

系统理解：

```text
clip_03.reference.add(reference.jpg)
```

CLI：

```text
reference add image.jpg
```

Agent：

```text
add_reference(
  clip="current",
  asset="image.jpg"
)
```

它们并不是三个功能。

而是一个动作的三种表达形式。

于是用户可以自然地在 GUI 和 CLI 之间切换。

简单的事情直接拖。

精确的事情用命令。

复杂的事情交给 Agent。

---

## 9. “一个模型，一个时间线类型”解决的是生成模型的语义问题

传统剪辑器默认所有东西最终都是：

```text
Video Track
Audio Track
```

但生成模型并不是这样。

视频生成模型可能关心：

Prompt、Reference、Duration、Seed、Extend。

音乐模型可能关心：

Section、Beat、Stem、Lyrics。

对话模型可能关心：

Speaker、Text、Emotion、Timing。

World Model 甚至可能关心：

State、Camera、Action、Event。

所以你的 Timeline 不应该强迫所有模型使用同一种数据结构。

更合理的是：

> **Timeline 是模型语义在时间维度上的 UI 表达。**

因此一个模型或一类模型，可以提供自己的 Timeline Type。

宿主软件只负责：

时间、选择、拖拽、Action、Modal、渲染、Undo、Agent Schema。

模型插件负责：

它的 Item 是什么，它能执行什么 Action，它的 Detail View 长什么样。

这就是为什么“模型时间线”最好做成可插拔基类，而不是写死在前端里。

---

## 10. 插件不能拥有自己的设计语言

可插拔不意味着插件可以自由发挥。

否则最后一定会变成：

A 模型一个 UI 风格，B 模型另外一个 UI 风格。

所以插件只能声明内容和能力：

```text
Title
Description
Fields
Actions
Items
Drop Rules
Agent Schema
```

宿主决定：

字体、间距、Modal、列表、菜单、错误显示、Loading、Selection。

也就是说：

> **Plugin provides semantics. Host provides interaction.**

插件提供“是什么意思”。

宿主提供“怎么表现”。

这能保证无论接入多少模型，软件仍然像同一个软件。

---

## 11. Pixel Style 不是复古，而是“确定性”

像素风格在你的产品中其实很合适。

因为它天然强调：

边界明确、状态明确、尺寸明确、层级明确。

所以你的像素视觉最好不是大量怀旧元素，而是一种高确定性的 UI：

固定栅格。

固定字号。

固定描边。

固定间距。

极少阴影。

有限颜色。

明确 hover / select / focus 状态。

文字尤其应该高度规范。

比如整个产品始终只有：

```text
TITLE

Description sentence.

Body / Content
```

Title 是“它是什么”。

Description 是“它做什么”。

Body 是“它的数据”。

Agent 返回、搜索结果、Modal、模型说明、错误信息都可以共享这个结构。

这样软件会形成非常强的一致性。

---

## 12. 信息也需要“单路径”

你前面提到的返回数量限制，其实和 UI 哲学是同一件事。

界面不能一次展示几十个按钮。

Agent 也不应该一次拿到 200 条结果。

所以系统应该天然支持：

```text
limit
filter
exclude
cursor
refine
```

比如 Agent 查询模型：

第一次：

```text
find video models
limit 5
```

发现都不合适。

第二次：

```text
find video models
exclude previous
filter image-reference
limit 5
```

也就是：

**Search → Evaluate → Exclude → Refine → Search**

而不是：

**Give me everything。**

这也是 Progressive Disclosure。

只是对象从“UI 功能”变成了“数据”。

所以可以说：

> 你的渐进披露应该同时存在于 UI 层、数据层和 Agent 层。

---

## 13. 整套软件最终应该追求“可预测”

极简并不是最终目的。

**可预测才是。**

用户应该逐渐形成非常强的直觉：

看到对象，我知道双击可以进去。

不知道还能干什么，就右键。

想让两个东西发生关系，就拖。

想精确描述复杂操作，就输入命令。

想做很多步骤，就告诉 Agent。

一旦这几个规则形成肌肉记忆，用户就不需要学习“功能在哪里”。

他们只需要理解：

**现在我面对的是什么对象？**

这是一种和传统软件非常不同的学习方式。

---

## 14. 所以这个产品实际上有五条最底层原则

如果以后整个团队只记住几句话，我觉得应该是这五条：

1. **作品优先于工具。** 默认界面只展示作品需要的空间，不展示功能目录。
2. **一个能力只有一条标准路径。** 不为了“方便”增加重复入口。
3. **双击进入，右键执行，拖拽建立关系。** 所有 GUI 都尽量服从这三个语法。
4. **复杂度按上下文出现。** 用户没有进入某个对象之前，与它有关的复杂度不应该存在。
5. **GUI、CLI、Agent 共用 Action System。** UI 只是系统的一种表达，不是系统本身。

最终它应该给人的感觉不是“这个软件按钮很少”，而是：

**这个软件似乎知道我现在正在做什么，所以只在我需要的时候让我看见下一件事。**

这才是这整套设计哲学真正有价值的地方。
